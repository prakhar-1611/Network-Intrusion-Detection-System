# Network Intrusion Detection System — CIC-IDS-2017

An ML-based NIDS that classifies real network flow data into BENIGN vs.
attack types (DDoS, PortScan, Brute Force, Web Attacks, Botnet,
Infiltration, DoS variants), with per-alert explainability and a small
SOC-style dashboard. Built on the CIC-IDS-2017 dataset from the
Canadian Institute for Cybersecurity.

## Why this is a solid "core cybersec" project

This isn't a generic Kaggle classification exercise — it's built around
real security concepts:

- **Real attack traffic**: CIC-IDS-2017 was generated by actually
  running DoS/DDoS tools, brute-force scripts, port scanners, and web
  exploits against a testbed and capturing the resulting flows with
  CICFlowMeter (the same tool used in many published IDS papers).
- **Class imbalance is the whole game**: ~80% of traffic is benign, and
  some attack classes (Heartbleed) have only a handful of flows. A
  model scoring 95% accuracy that never predicts "Heartbleed" is
  useless in a SOC — this project evaluates and discusses that
  explicitly instead of hiding behind accuracy.
- **Data leakage awareness**: Source/Destination IP and timestamps are
  dropped deliberately, because leaving them in lets a model
  "memorize" which IP was the attacker in this specific 2017 capture
  instead of learning generalizable traffic behavior — a classic
  mistake in published IDS work worth being able to talk about.
- **Explainability for triage**: SHAP is used to show *why* a flow was
  flagged, which is what a SOC analyst actually needs before deciding
  whether to block or dismiss an alert.

## Project structure

```
nids-cicids2017/
├── data/
│   ├── raw/            # put the downloaded CSVs here
│   └── processed/       # cleaned parquet output lands here
├── src/
│   ├── preprocess.py    # load, clean, dedupe, drop leaky columns
│   ├── train.py         # train RandomForest or XGBoost (binary/multiclass)
│   ├── evaluate.py       # precision/recall/F1 per class, confusion matrix, ROC-AUC
│   └── explain.py        # SHAP global + per-flow explainability
├── app/
│   └── dashboard.py      # Streamlit "alert console" demo
├── models/                # trained model + test split land here
├── reports/               # classification report, confusion matrix, SHAP plot
└── requirements.txt
```

## Setup

```bash
python -m venv venv && source venv/bin/activate   # or your preferred env manager
pip install -r requirements.txt
```

## 1. Get the data

Download the CSVs from the link you have (CIC-IDS-2017 CSVs) — it's the
8 files covering Monday through Friday of the capture (e.g.
`Monday-WorkingHours.pcap_ISCX.csv`,
`Tuesday-WorkingHours.pcap_ISCX.csv`,
`Wednesday-workingHours.pcap_ISCX.csv`,
`Thursday-*-WebAttacks.pcap_ISCX.csv`,
`Thursday-*-Infilteration.pcap_ISCX.csv`,
`Friday-*-DDos.pcap_ISCX.csv`,
`Friday-*-PortScan.pcap_ISCX.csv`,
`Friday-WorkingHours.pcap_ISCX.csv`). Put all of them, unzipped, into
`data/raw/`. Combined they're about 2.8M rows / ~1GB — expect the first
run to take a few minutes.

## 2. Preprocess

```bash
python src/preprocess.py --raw_dir data/raw --out data/processed/cicids2017_clean.parquet
```

Prints the class distribution as it runs — worth screenshotting for
your report/README, it's the single best visual for explaining the
imbalance problem.

## 3. Train

```bash
# Multiclass (which attack?) with Random Forest
python src/train.py --data data/processed/cicids2017_clean.parquet --target multiclass --model rf

# Or XGBoost, or a binary BENIGN-vs-ATTACK model
python src/train.py --target multiclass --model xgb
python src/train.py --target binary --model rf
```

## 4. Evaluate

```bash
python src/evaluate.py --model models/rf_multiclass.joblib --test_split models/rf_multiclass_test_split.joblib
```

Look at **recall per attack class**, not overall accuracy — that's the
number that tells you what the model would actually miss in
production.

## 5. Explain

```bash
python src/explain.py --model models/rf_multiclass.joblib --test_split models/rf_multiclass_test_split.joblib
```

Generates a global feature-importance plot (which flow features drive
detections overall — usually flow duration, packet length stats, and
flow bytes/packets per second).

## 6. Run the dashboard

```bash
streamlit run app/dashboard.py
```

Lets you step through individual test flows and see the prediction,
a severity rating, and the top SHAP-driven features behind it — a
mini version of what a SOC analyst sees at an alert console.

## Extending it further (good "stretch goal" talking points)

- **Adversarial robustness**: perturb a few flow features slightly
  (e.g. pad packet sizes, slow down timing) and see if a DoS flow can
  be pushed across the decision boundary into BENIGN — ties directly
  into evasion techniques real attackers use against ML-based IDS.
- **Concept drift**: train only on Monday-Thursday, test on Friday's
  attack types the model never saw during training, and discuss why a
  static model degrades over time in production.
- **Real-time capture**: swap the static CSVs for live traffic via
  CICFlowMeter or `pyshark`, feeding flows into the trained model as
  they're captured.
- **Feature selection**: correlation/SHAP-driven pruning of the ~78
  raw features down to a smaller set, and discuss the
  detection-accuracy vs. compute-cost trade-off for deployment on
  resource-constrained network appliances.

## Interview talking points this project gives you

- Precision/recall trade-offs and why accuracy is a misleading metric
  for imbalanced security data.
- Concrete example of data leakage in a security ML pipeline and how
  you caught/avoided it.
- How explainability (SHAP) turns a black-box classifier into
  something a SOC analyst can act on.
- The gap between offline evaluation and real deployment: false
  positive fatigue, concept drift, and adversarial evasion.
